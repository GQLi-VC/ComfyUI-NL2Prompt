## 7. P0 缺陷档案（本次验收最重要的发现）

### 7.1 现象（首次实测）

提交「`NL2PromptLoadLLM` 输出已接给 `NL2PromptComposer.llm` + `use_llm=true` + 云端模式无 api_key」后：
任务永久停在 `queue_running`，`/history/<id>` 恒为 `{}`；`POST /interrupt`（HTTP 200）与 `POST /queue {"clear":true}` 均**无效**（running 清不掉）；新任务永远停在 pending。约数分钟后进程**完全退出**（端口无 LISTEN，连接被拒）。

### 7.2 根因链（已最小复现）

`test_env\logs\comfyui_test_20261115_233605.stderr.log` 第 127–130 行：
```
object type name: UnicodeEncodeError
object repr: UnicodeEncodeError('gbk', '...llm_client.LLMError: llm_key_missing: 云端模式未配置 api_key
             （请在「LLM 设置 › 运行设置」中填写，或设置 ANIMA_LLM_API_KEY_<供应商大写> / ANIMA_LLM_API_KEY）', 175, 176, 'illegal multibyte sequence')
lost sys.stderr
```

1. `nodes.py` 抛 `LLMError`，其 detail 文案含 **`›`(U+203A)**；
2. 测试环境 ComfyUI 进程 stderr 编码 = **gbk**（当时 `start_test.ps1` 未启用 UTF-8）；
3. `›` **无法用 GBK 编码** → `UnicodeEncodeError('gbk', …, 'illegal multibyte sequence')`；
4. stderr 被写坏 → `lost sys.stderr` → **prompt worker 线程死亡** → 队列永久卡死 → 进程最终退出。

**最小复现**（字符级实证）：
```python
'›'.encode('gbk')   # UnicodeEncodeError: 'gbk' codec can't encode character '\u203a' … illegal multibyte sequence
'「'.encode('gbk')  # OK  b'\xa1\xb8'   ← 其余中文符号均可编码，唯 U+203A 不可
```
全仓扫描结论（lead 复核）：`plugin/` 下 7 个 py 文件中，GBK 不可编码字符**仅此 1 处**。

### 7.3 影响面

不只是测试环境：**用户正式环境 `<你的ComfyUI根目录>` 同为中文 Windows / GBK**。任何用户走「云端模式但未配置密钥」这条极常见的路径，都会把 ComfyUI 出图队列打挂（表现为「点执行没反应、之后再也出不了图」），属阻断级。

#### 11.9.3 关键发现：校验器存在"negative 覆盖度"盲区（skill 不是过严，是**过松**）

- R1 的 negative 只压了原皮词的一部分（有 `frilled dress / detached collar / detached sleeves / elbow gloves / mismatched gloves / white thighhighs / gradient legwear`，**缺 `strapless dress / purple dress / purple sleeves / clothing cutout`**）；
- R2 的 negative **一个原皮词都没有**（只有通用负面 + 姿态互斥词），却仍被判 `ok:true`；
- 根因：`check_anima(positive, negative, required_tokens, forbidden_tokens, skill)` 把 `forbidden_tokens`（=原皮抑制词）用于「positive **不得含**」，**没有**任何参数校验「negative **必须含**」。所以 LLM 漏压负面词时校验器无法发现，`retried` 也不会触发。
- 次生问题：R2 的 negative 出现自相矛盾的 `day` 与 `night`、`standing` 与 `lying`、`legs together` 与 `spread legs` 同时存在 —— LLM 在"冲突抑制"上自由发挥过度。
- 对比模板模式：模板 negative **必定**包含全部 11 个原皮词（差集抑制）；所以当前 **LLM 模式的 negative 质量低于模板模式**。

### 12.4 遗留 FAIL（如实记录，未放宽断言）

**C7｜非法 id 返回 `bad_skill_id`（lead 判据，含 `/skills/delete`）**

```
POST /nl2prompt/skills/delete  {"id": "../evil"}
→ HTTP 200 {"ok": false, "error": "skill_not_found", "detail": "skill 不存在：../evil", ...}
```

实现事实（`plugin/routes.py`）：

- 写入口 `POST /nl2prompt/skills/new` **有** `_SKILL_ID_PATTERN` 预校验 → 返回 `bad_skill_id`（本用例该条 **PASS**）；
- 读/删入口（`GET /skills/{id}`、`POST /skills/delete`）**不做格式预校验**，
  而是拿 id 去比对 `index.json` 的白名单 → 不命中即 `skill_not_found`。

安全面评估：白名单方式**不存在路径穿越风险**（只有已存在的合法 id 才会被读取/删除），
但与 lead 判据「非法 id → `bad_skill_id`」不一致，故**判 FAIL** 而非放过。

处置建议（二选一，交 lead 裁决）：

1. 实现侧：在 `_handle_skill_delete` / `_handle_skill_detail` 入口复用 `_SKILL_ID_PATTERN`，命中失败即返回 `bad_skill_id`；
2. 判据侧：承认白名单更安全，把 delete/detail 的非法 id 口径改判为 `skill_not_found`，并把 `bad_skill_id` 的适用范围写明为「仅写入口」。
